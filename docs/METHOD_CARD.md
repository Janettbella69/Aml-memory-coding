# aml-memory — method card

Entry for the Agent Memory Leaderboard (AML) Cycle 2, Textual Memory track, Open-source Methods division.
This is the disclosure the platform requires for reused work: original authors, technical report, and every method change.
Describes code version **1.0.0** (2026-10-20, git tag `v1.0.0`); the version list at the end records every change since 0.1. Repository facts about prior work were checked on 2026-10-07 (repository pages, GitHub REST API, LICENSE files, arXiv).

## System overview

aml-memory is a retrieval service: Search returns stored conversation text and nothing else. Add stores every incoming turn as raw text in SQLite (one database file per `user_id`) and indexes it twice: a porter-stemmed FTS5 word index, and a character-trigram FTS5 index that only receives turns containing CJK text. Search turns the question (plus any multiple-choice options) into OR-joined FTS5 queries, ranks turns with BM25 (reciprocal-rank fusion when both indexes fire), orders near-equal hits newest-first, places the user's standing rules and preferences after the first few hits, expands each hit with the two turns before and after it, renders every turn as `[YYYY-MM-DD HH:MM UTC] ROLE: text`, de-duplicates turns already shown, and stops at `top_k` results or ~100k tokens. Nothing matched → the newest turns. That much is deterministic. The submitted configuration adds two model calls: every turn is also embedded with `text-embedding-v4` (256 dims) and the question's dense neighbours are fused behind the first five lexical hits, and one `gpt-4o-mini` call per Search proposes up to three extra keyword queries and a date range, fused the same way; if either call fails, the deterministic result is returned. There is no reranker and no other model. Search returns evidence only and never generates or paraphrases an answer.

## Add pipeline (`POST /v1/memories/add`, alias `/add`)

1. Validate the body (`request_id`, `messages[≥1]`, `user_id`, `session_id`; unknown fields ignored; blank identifiers → 422).
2. Fingerprint the canonical JSON of the body (SHA-256, sorted keys). `INSERT OR IGNORE` the `request_id` into `ingest_log`: a replay with the same fingerprint returns 200 without writing; the same `request_id` with a different fingerprint returns 409. The insert takes SQLite's write lock, so concurrent replays serialise correctly.
3. Position inside the conversation: `pos = 1000 × N + message_index`, `N` = ordinal parsed from `request_id` (`chunk-N`, also `part|seg|msg`). Without an ordinal, the next free block of that `(user_id, session_id)` is used.
4. For each message: flatten the content to text (strings as-is; multimodal `text` parts concatenated, `image_url` parts dropped); skip empty text; `id = "mem_" + blake2b(request_id ␟ index)`; `standing = 1` when the role is `user` and the text matches the standing-rule patterns (English: `from now on`, `whenever`, `please always/never/don't …`, `don't/never/always/only + assistant-facing verb`, `remember that/to`, `call me`, `I prefer`, `my rule`, `new/ground/format rule`, `forget what/the …`, `must be/use/…`, `no longer`, `remind me`, allergy/dietary words; Chinese: 以后/今后/别再/不要/一定要/记住/规则/只做/过敏/素食/叫我/忘掉 …).
5. Insert into `memories` (role, text, `event_ms` = message timestamp if supplied, `pos`, `standing`, `stored_at`), into the word index (`porter unicode61 remove_diacritics 2`, an external-content FTS5 table so the text is stored once), and — only when the text contains CJK characters — into the trigram index, as the CJK-only string (punctuation, spaces and Latin tokens removed so trigrams span them). All of this lives in the user's own database file `<DATA_DIR>/users/ab/cd/<blake2b(user_id)>.db`, so a query can only ever see one user's turns.
6. Commit (SQLite WAL, `synchronous=NORMAL`, 30 s busy timeout) and only then return `{"success": true, request_id, user_id, session_id}` echoed byte-for-byte.

## Search pipeline (`POST /v1/memories/search`, alias `/search`)

Input `{query, options?, user_id, top_k}` (`top_k` 1–1000, default 100). Output `{"data": [{id, content, score, created_at}]}` in rank order, never more than `top_k` items.

1. **Word hits.** Terms = `\w+` tokens of `query` + `options`, lower-cased, ≥ 2 characters, stop list removed (our own 120-word list), CJK tokens excluded, de-duplicated in order. Terms of ≥ 5 characters also match as prefixes (`"term"*`); all OR-joined so partial matches still rank. FTS5 `bm25()` with weight 0 on `utok`, 1 on `content`; limit `2 × top_k`.
2. **Trigram hits.** Overlapping character trigrams of the CJK-only text of `query` + `options`, OR-joined, against the trigram index. When both lists are non-empty they are fused by reciprocal rank fusion (k = 60); otherwise the non-empty one is used.
   - **Dense neighbours** (submitted configuration, 0.5). The question with its options is embedded with `text-embedding-v4` (256 dims) and compared with the user's stored turn vectors (float16, numpy dot product). The first `DENSE_HEAD=5` lexical hits keep their places; the dense list is fused with the rest by reciprocal rank fusion, and the recency band (step 3) is applied to the head and the fused tail separately. An embedding failure leaves the lexical list.
   - **Query planner** (submitted configuration, 0.3). One `gpt-4o-mini` call sees the question and the first 8 results (400 characters each) and returns at most 3 extra keyword queries and an optional date range. The extra queries run through steps 1–2 and are fused behind the same five-hit head; with a date range the original question is also searched inside the period (dense included) and in-range hits move ahead of the rest. The model's text is never returned; on an error or a 20 s timeout the first-pass list is used.
3. **Recency band.** Scores are normalised to the best hit. Hits are grouped into bands of width `RECENCY_BAND` (0.2); inside a band the newer memory (`event_ms`, then `pos`) comes first. Purpose: a value that was later overwritten must not outrank its replacement merely because the older sentence is shorter.
4. **Standing rules.** The user's newest `standing` turns (up to 4 × the budget) are sorted by "also a hit for this query" first, then newest; the first `min(RULE_SLOTS=6, top_k // 4)` are kept.
5. **Order.** The first `LEAD_HITS=5` hits, then the rules, then the remaining hits. No hits at all → the newest `FALLBACK_RESULTS=10` turns with `score = 0`.
6. **Assembly.** Walk the ordered list; skip a hit whose turn is already visible inside an earlier block (rules are never skipped); each hit and each rule becomes a block of its `±CONTEXT_WINDOW=2` neighbouring turns in conversation order (`pos`, crossing Add-chunk boundaries), one rendered turn per line; fallback turns are returned alone. Stop at `top_k` results or `MAX_RESPONSE_CHARS=400 000` characters (≈ 100 k tokens; the platform keeps a 117 760-token prefix in rank order). `score` = normalised BM25 (4 dp; rules without a hit score get 1.0); `created_at` = storage time; a malformed MATCH expression is treated as "no hits"; an unknown `user_id` yields `[]`.

Rendering: `[2024-01-01 00:00 UTC] USER: I adopted a cat named Luna.`; the stamp is omitted when the message has no valid timestamp. A turn with relative-time phrases gets a note resolved against its own stamp, e.g. `(dates: yesterday = 2025-04-26)` (0.4). `created_at` of a result is the hit turn's own timestamp, or absent (0.8).

## Models used

**Submitted configuration (1.0): `text-embedding-v4` at Add and Search (dense channel) and `gpt-4o-mini` at Search (query planner). No reranker, no generative model in Add, no other model.** By version:

- **0.2 (default configuration): none.** No LLM, no embedding model, no reranker. Add and Search are pure SQLite/FTS5 code paths.
- **0.3 (optional, off unless `PLANNER_MODEL=gpt-4o-mini` is set):** one `gpt-4o-mini` chat call per Search, temperature 0, JSON output, ≤ 200 output tokens. Input: the question (and options) plus the first 8 first-pass results truncated to 400 characters each. Output: up to 3 extra keyword queries and an optional date range. The extra queries are run through the same BM25 indexes and fused by reciprocal rank fusion; in-range hits are moved ahead when a date range is given. The model's text is never returned to the caller; on timeout (20 s) or any error the deterministic result is returned. The submitted configuration runs with it ON (`PLANNER_MODEL=gpt-4o-mini`); the frozen `.env` values are listed under 1.0. Provider note (2026-10-08): the calls go through OpenRouter (`OPENAI_BASE_URL=https://openrouter.ai/api/v1`, model id `openai/gpt-4o-mini`), which routes to the same OpenAI `gpt-4o-mini` model; no other model is reachable from the code path. `scripts/judge_local.py` reads `JUDGE_MODEL` for the same reason.
- Platform rule, verbatim from the Full-evaluation checklist (2026-10-07): "Open-source Methods entries are expected to use gpt-4o-mini during Add. Commercial Products entries have no Add/Search model restriction." The competition FAQ (Chinese) adds: embedding models on the open-source board must be `text-embedding-v4`, LLM components must be `gpt-4o-mini`, rerankers are unrestricted, and systems using self-trained or other open-weight models are directed to the commercial board.
- **0.7:** `qwen3-rerank` as the reranker (Model Studio; rerankers are unrestricted on the academic board). `gte-rerank-v2`, `qwen3.7-text-rerank`, Voyage, Cohere and Jina are supported alternatives, declared only if used. **Not used by the submitted system (0.10, 2026-10-15): the reranker is off, so the only models called are `text-embedding-v4` and `gpt-4o-mini`.**
- Organisers' written answer (email to contactus@agentmemoryleaderboard.ai sent 2026-10-09, reply received by 2026-10-15): the newer `qwen3.7-text-embedding-flash` / `qwen3.7-text-embedding` models are not accepted on the open-source board; `text-embedding-v4` is the only embedding model.
- Commitment: if a later version adds any model call it will be `gpt-4o-mini` only (Add and/or Search); any embedding would be `text-embedding-v4` only. The declared configuration will name every model used; "no model" is declared explicitly for 0.2.

## Method changes by version

Numbers are from our own written mini-set (`evalset/`, fictional conversations, 7 capability groups; never leaderboard data), retrieval-only metrics at `top_k = 100`.

- **0.1 (2026-10-07, commit `f09d825`).** Plain FTS5/BM25 over raw turns plus: `is_rule` tagging at Add; in-conversation ordering from the `request_id` ordinal; user scoping inside the FTS table; prefix matching from 4 characters; 8 newest rules prepended with score 1.0; ±1 neighbour context; timestamp/role rendering; recency fallback; multimodal parts flattened; three auth schemes; retention sweep at start. 65 questions: hit@10 0.78, hit@100 0.97, MRR 0.20, trap-order 0.17.
- **0.2 (2026-10-07).** Rewritten (see §1 above) and re-ranked:
  - Porter-stemmed word index (`targeting` now finds `target`); prefix matching from 5 characters.
  - Character-trigram index for CJK turns (unicode61 cannot segment Chinese), fused by RRF; Chinese standing-rule patterns.
  - Recency band 0.2: newest-first among near-equal scores ("latest value wins"). Rules relevance-sorted and placed after the first 5 hits instead of before everything; budget 6 instead of 8; tighter rule patterns (assistant-facing verbs; "he always does" is no longer a rule).
  - Context ±2 crossing Add-chunk boundaries; blocks de-duplicated (a hit already visible in an earlier block is skipped); `MAX_RESPONSE_CHARS` cap.
  - One SQLite file per `user_id` (physical isolation; query cost independent of the corpus size), cached connections with per-file locks, per-process search/write gates, external-content word index, WAL size limits and idle eviction; insert-first idempotency; CJK-only trigram index (English corpora pay nothing for it); periodic retention sweep every 6 h in addition to start-up; uvicorn factory mode (no import-time side effects); Docker image installs from `uv.lock`.
  - Chosen by `scripts/sweep_local.py` over `RECENCY_BAND ∈ {0, .1, .2, .3, .5} × LEAD_HITS ∈ {3, 5} × RULE_SLOTS ∈ {4, 6, 8} × CONTEXT_WINDOW ∈ {1, 2}`.
  - 71 questions (65 + a Chinese sample): hit@10 0.92, hit@100 1.00, MRR 0.72, trap-order 0.85, ≈ 2.1 k tokens per response. Remaining misses: a two-hop question with no lexical overlap between hops (`lt-co-03`), and a stance change where the older statement is shorter (`lt-te-02`).
  - Tests: 21 (`tests/test_api.py`, `tests/test_search_v02.py`, `tests/test_evalset.py`).
- **0.3 (2026-10-07, implemented, default off).** `app/planner.py`: one-step gpt-4o-mini query planner (see "Models used"), after ReFind's agent-controlled search idea but reduced to a single bounded step with a deterministic fallback; `scripts/judge_local.py`: end-to-end proxy scoring (gpt-4o-mini answers from our Search output, gpt-4o-mini grades against the reference). Judge comparison on our own set (2026-10-08, two runs each, `openai/gpt-4o-mini` via OpenRouter, 76 questions): planner OFF 0.868 / 0.868, planner ON 0.908 / 0.908; temporal 0.750 → 1.000 in both ON runs, governance 0.700 → 0.700 / 0.800, execution 0.933 → 0.867 (one near-identical answer judged differently, i.e. grader noise); the planner fixed 5 questions and lost 1–2. Decision: ON in the submitted configuration. Raw rows in `evalset/results/judge-v0.3-planner-{off,on}*.json`. Tests: `tests/test_planner.py` (fake planner).
- **0.4 (2026-10-08).** (a) `app/timex.py`: relative-time notes rendered after a turn — "(dates: yesterday = 2025-04-26; 三周前 = week of 2025-06-09)" — resolved only from the turn's own timestamp, English and Chinese phrase tables, days/weeks/months/years at matching granularity, at most 4 notes, render-time only (the index stays raw). Idea after InvMem (Cycle-1 #1; see `CYCLE1_NOTES.md`), own rules and tables; aimed at the board-wide weakest leaf "Dates, Relative Time & Intervals". Same-period phrases (today, this week, 今天, 本月) are not annotated: the stamp already says so and a first judge run showed them as clutter. Judge on the 15 temporal questions (planner off, two runs each): notes ON 0.867 / 0.867, notes OFF 0.733 / 0.733 — the two questions fixed need "三周前" and "today … Priya started today" resolved against the stamp. `TIME_NOTES=0` disables. (b) `OPTIONS_MODE`: how multiple-choice options enter retrieval — `append` (query + options, as before and as InvMem did), `none` (question only), `channel` (options as a separate RRF channel weighted by `OPTIONS_WEIGHT`, after Hybrid Episodic Memory's option channel, Cycle-1 #6). Added because the official FAQ Q14 warns against splicing all options into the retrieval text without judgement. Tests: `tests/test_timex.py`, `tests/test_v04.py`. Evalset v2: +8 questions (relative-time EN/ZH, multiple-choice with in-conversation distractors).
- **0.5 (2026-10-09).** Dense channel `app/embed.py` + `store.dense_search`: every turn is embedded at Add time with `text-embedding-v4` (256 dims, float16, stored in the user's own SQLite file), the question (plus options in append mode) is embedded at Search time, cosine neighbours are fused by reciprocal rank fusion with the word and trigram lists (`DENSE_WEIGHT`, default 1.0) and, when the planner gives a date range, into the date-restricted list too. Why: on the Cycle-1 board the whole open-source gain over plain BM25 came from evidence without lexical overlap (composition +7.5, fact recall +5.3 for InvMem; see `CYCLE1_NOTES.md`) and a dense + BM25 fusion is the common ingredient of #1, #3, #4, #6, #9. Idea credit: InvMem, Hybrid Episodic Memory (both RRF of BM25 and dense); code is ours. Operational: batches of 10 (service limit), token-bucket pacing for the 1,800 req/min key limit, retries with backoff, a failed embedding degrades that turn to lexical-only and a background loop back-fills it; `meta` pins model:dims per file. Models used: `text-embedding-v4` (the only embedding model allowed on the academic board) via Alibaba Model Studio, China region. Tests: `tests/test_dense.py`, `tests/test_embed_client.py`. Local set (84 q, deterministic): dense OFF hit@10 0.924 / hit@20 0.987 / MRR 0.695; dense ON (w=1.0, 256 d) hit@10 0.924 / hit@20 1.000 / MRR 0.550; w=0.5 MRR 0.535; w=1.5 hit@10 0.911; 1024 d hit@10 0.886 — on our own lexical-overlap questions the dense list pushes exact hits down the head of the list without changing top-20 recall. Judge (84 q): dense ON + planner OFF 0.869, dense ON + planner ON 0.869, vs planner ON without dense 0.881 (noise band ±0.02). Decision deferred to the organisers' public LoCoMo-Refined data (`scripts/eval_public.py`), which has the paraphrase gap our set lacks; Public LoCoMo-Refined (organisers' source data, 1,376 scored questions, deterministic, planner off): lexical only → hit@1 0.578 / hit@10 0.828 / hit@20 0.909 / hit@100 0.975 / all-evidence@20 0.823 / MRR 0.683; dense RRF (w=1.0, 256 d) → hit@1 0.390 / hit@10 0.839 / hit@20 0.926 / hit@100 0.991 / all@20 0.847 / MRR 0.573. Dense raises deep recall (multi-hop hit@10 0.712 → 0.764, temporal hit@20 0.886 → 0.930, 22 more questions with evidence anywhere in the 100) but lets semantic neighbours crowd the head of the list (rank-1 0.578 → 0.390). Hence `DENSE_HEAD`: the first N lexical hits stay in front, the dense list is fused only behind them; Head sweep on the same public set (after fixing a scale bug: the recency band is now applied to the lexical list and the fused tail separately): head 0 → hit@1 0.373 / hit@20 0.921 / hit@100 0.991 / MRR 0.561; head 5 → 0.578 / 0.925 / 0.989 / 0.684; head 10 → 0.578 / 0.924 / 0.989 / 0.684; head 20 → 0.578 / 0.914 / 0.988 / 0.684; lexical only → 0.578 / 0.909 / 0.975 / 0.683. **Default `DENSE_HEAD=5`**: the lexical head keeps rank-1 precision and MRR, the dense tail adds the deep recall (hit@100 +1.4 points = 19 more questions with evidence in the list; multi-hop hit@20 0.873 → 0.887, temporal 0.886 → 0.903). Judge on 200 public questions (first 20 per conversation: 77 multi-hop, 99 temporal, 20 open-domain, 4 single-hop; gpt-4o-mini answers from our list, gpt-4o-mini grades against the gold list): lexical top-100 0.610; dense-head-5 top-100 **0.655** (multi-hop 0.662, temporal 0.697, multimodal 0.616); dense-head-5 top-20 0.625 at one fifth of the tokens; dense-head-5 top-10 0.550 (recall@10 0.780) — so the full top-100 stays, more context helps this reader (as ActiveMemoryIndex also found); dense-head-5 + planner with the head re-ranked by the expansion 0.605 although recall@100 was 1.000 (hit@1 fell to 0.140) → the planner expansion now keeps the lexical head in front and a date range reorders the whole list; re-measured with the head kept: dense-head-5 + planner **0.665** (hit@1 0.415, hit@20 0.835, hit@100 0.980; temporal 0.707, multi-hop 0.662) — the best configuration, +1 point over dense-only (within noise, never negative) at +2.5 s per Search. Reading: the answer model's accuracy follows the head of the list, not recall@100. **Submitted configuration (v0.5 → v1.0): text-embedding-v4 256 d, DENSE_HEAD=5, gpt-4o-mini planner ON, full top-100, time notes ON, options appended.**
- **0.6 (2026-10-09, optional, off by default).** `app/selector.py`: one gpt-4o-mini call per Search *after* retrieval — the question plus the first `SELECTOR_CANDIDATES` (40) blocks → the numbers of the blocks that hold evidence (≤ 8) and a question kind (fact / task / other); `search.apply_selection` moves those blocks to the front; for 'fact' questions `SELECTOR_TAIL` may cut the unselected tail (standing rules always kept); scores re-issued monotonic. Only the order of verbatim blocks changes; any failure keeps the deterministic order. Motivation — the window-arms experiment on the organisers' public LoCoMo-Refined data (144 questions, same Search list, four contexts, gpt-4o-mini reader): full top-100 0.778 · top-10 0.688 · evidence blocks only 0.847 · evidence blocks first + full tail 0.819 — the reader fails ~13 % of single-hop questions it was handed the evidence for, so the head of the list, not recall (evidence inside the top-100 for 99.3 %), is the lever. Measured with the real selector on the same questions: reorder-only 0.806 (wins 9 / losses 5; evidence at rank 1 0.50 → 0.75); tail-20 0.722 (wins 6 / losses 14) → truncation rejected. Selector cost ≈ 12 k input tokens per Search. Tests: `tests/test_selector.py`.

## Data handling

- No query or memory text in logs: Add logs nothing per request; Search logs the result count and `top_k` only; uvicorn access logs carry path and status only.
- Strict isolation is physical: each `user_id` has its own SQLite file; a Search opens the file of the `user_id` it was given and nothing else, and an unknown `user_id` creates no file and returns `[]`. `session_id` is only used to find neighbours. Covered by `test_user_isolation` and `test_users_live_in_separate_files`.
- Retention: `RETENTION_DAYS` (1–30, default 30). `delete_expired()` runs at process start and every `SWEEP_HOURS` (6) while the service is up and deletes every user database whose last write is older than the window. After the Full run the operator additionally deletes the volume (`docker compose down -v`) — platform rule: delete within 30 days after job completion.
- Evaluation data is used only to serve the run: no training, no fine-tuning, no analysis outside the job, no redistribution. Local tuning uses our own written mini-set under `evalset/`.
- Secrets: `MEMORY_API_KEY`, `OPENAI_API_KEY` and `DASHSCOPE_API_KEY` come from the environment (`.env`, git-ignored); nothing is committed.
- Model calls: the embedding call carries turn texts and the question; the planner call carries the question, its options and the first 8 results. Both go only to the declared model providers; our logs record error types, never text.

## Capacity declaration

- Add concurrency: 16. Search concurrency: 16. `top_k`: 1–1000 (outside → 422); official runs use 100.
- Add is synchronous: the turns are committed to the user's SQLite file (WAL) and indexed before the 200 is returned; idempotent replay is safe; concurrent replays serialise on the `ingest_log` insert.
- Deployment: `UVICORN_WORKERS` (default 2) uvicorn processes; inside each process a gate allows `SEARCH_PARALLELISM=1` search and `WRITE_PARALLELISM=2` Add transactions at a time (SQLite serialises allocations behind one process-wide mutex, so more threads per process only add contention); connections are cached per user file (LRU 512, closed after 120 s idle, which also checkpoints and removes the WAL). Docker image from `ghcr.io/astral-sh/uv:python3.12-bookworm-slim` with dependencies installed from `uv.lock`; volume `/data`; health check every 30 s; the production compose file in `deploy/` runs Caddy for TLS.
- Measured on 2026-10-07 (Apple M-series laptop, synthetic Zipf text, 300 users × 600 turns, 16 concurrent clients, `scripts/soak_local.py` + ApacheBench): one worker — Add 1,313 calls/s (p50 12 ms, p99 21 ms), Search 293 q/s (p50 53 ms, p99 60 ms, 135 k-character responses at `top_k=100`); the same server with 16 searches allowed per process managed 24 q/s at 412 % CPU, which is why the gate exists. A single search on a 2,000-turn user costs 5 ms end-to-end over HTTP. With the default two workers: Add 2,290 calls/s (p50 7 ms, p99 12 ms), Search 497 q/s (p50 28 ms, p99 39 ms).
- Timeouts: no server-side request timeout; the platform allows up to 30 minutes per request. Proxy timeout should be ≥ 60 s (the Caddyfile sets 1800 s).
- Storage: the official site states the Textual track spans ≈ 300 M tokens (~1.2 GB of text). Measured: 38 MB of synthetic text → 184 MB on disk at rest (memories table + porter index + per-file overhead), i.e. ≈ 5×, so ≈ 6 GB for the whole track plus ≤ 4 MB of WAL per active user. Budget ≥ 20 GB of disk. Deployed soak (2026-10-08, from a laptop in the US through TLS to the Alibaba Cloud box, planner ON): 200 users × 30 chunks × 20 messages ≈ 4.2 M words at concurrency 16 → 6,000 Adds in 96 s (62.5 adds/s, 1,250 msgs/s, 0 errors; p50 234 ms, p90 257 ms, p99 454 ms, max 1.7 s, dominated by round-trip time); 288 Searches at 16-way → 6.2 q/s, p50 2.2 s, p90 3.3 s, p99 5.0 s, max 5.9 s (the gpt-4o-mini planner call dominates; without it the local p99 is 39 ms); median response 135 k chars ≈ 34 k tokens. Disk free on the box: 34 GB. Extrapolated Add time for ≈ 300 M tokens: ≈ 1.5 h at this client distance.
